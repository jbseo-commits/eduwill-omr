## 학과별 합격선 — 왜 배포본에서 «덧대는가»

응시한 시험지의 학교를 잡아 그 학교 **학과별 합격선을 상위권·중위권·하위권 세 줄**로 보여준다
(`admFor()` → `admHTML()`). 지망교가 아니라 **응시 학교** 기준이다.

🔴 **원본 빌더가 내보내는 범위로는 3개교(단국대·가천대·한성대)뿐**이라 대부분의 시험지에서
박스가 아예 안 떴다. 빌더는 학교가 «공식 발표»한 입시결과만 쓰는데, 영어 고사 + 학과 단위로
남는 것이 그 셋뿐이기 때문이다.

`adm_expand.py` 가 **배치상담 5개년 점수 워크북**(`data/admissions/admissions_workbook.json` ·
23개교 6,727행 · 전부 실측 최종등록자 평균)을 덧대어 넓힌다.

```
시험지 커버리지   6/46 → 38/46          (연도·시험지 조합 기준 99/119 · 83%)
ADM               3개교 → 24개교 · 112개 (학교·연도) · 4,000행
파일 크기         1,597,530 → 1,834,368 B  (+231 KB)

**여전히 없는 8종** — 광운대(2) · 덕성여대(3) · 세종대 · 수원대 · 아주대. 두 출처 어디에도 자료가 없다.

🔴 **왜 빌더를 안 고치고 배포본에 덧대는가** — `scripts/build_omr_app_v2.py` 가
**Codex 락(2026-08-31 12:10 · 진행중)** 아래에 있다. 락이 풀리면 빌더가 워크북을 직접 읽게 고치고
**`배포.sh` 3단계를 지우는 것이 맞다.**

### 🔴 추정치(`admissions_estimated.json` 4,434건)는 넣지 «않았다»

2026-08-06 크로스체크가 이미 기각한 데이터다.

- 생성기가 `BASE_SCORE 75.0` + 수기 티어 + `random.uniform(-0.5, 1.0)` 이라 **실측 점수 열을 읽지 않는다.**
- 백테스트 — MAE 5.2점 · 편향 +4.3점 · **학과 순위상관 중앙값 0.11**(항공 −0.43 · 한성 −0.40).
  학과별 표의 존재 이유인 「어느 학과가 더 높은가」가 담겨 있지 않다는 뜻이다.
- `CLAUDE.md` 7대 원칙 2항(근거 없는 합격 점수 추정 금지)에 정면으로 걸린다.

되살리려면 **실측에서 뽑아 백테스트를 통과시킨 뒤**에 할 것. 공식을 손보는 방식은 이미 기각됐다.

### ⚠️ 이 값은 «커트라인»이 아니다

워크북 자신의 경고다 — *"최종등록자 «평균»이다. 합격선(커트라인)이 아니며 실제 커트는 이보다 낮다."*
그래서 `basis="평균"` 을 그대로 실어 보내고, 앱이 머리말에
**「학교 발표값은 등록자 평균이라 실제 커트라인은 이보다 낮다」**를 띄운다. 이 문구를 지우지 말 것.

📌 한 학교·연도·계열에 `일반`·`학사` 가 섞이면 **`일반` 만** 쓴다(점수대가 계통적으로 달라
섞으면 상·중·하위권 줄이 왜곡된다). `일반` 이 없을 때만 `학사` 로 대체한다.

## 🔴 목표 문항 수 — «점수»와 «문항»을 섞어 쓴 사고 (2026-08-31)

학생 리포트 뒷면의 「여기까지 잡으면 상위 30%에 도달합니다」 가로줄이 엉뚱한 자리에 그어졌다.
2022 건국대(1-20번 3점 · 21-40번 2점 · 100점 만점)에서 **56점 학생에게 「틀린 19개 중 18개를
잡아라」**라고 안내했다. 실제로는 **7~9문항**이면 된다. 피드백이 이미 나간 뒤라 즉시 고쳤다.

원인은 한 줄이다 — `s.gapTop` 은 «점수» 차인데(73.5 − 56 = 17.5 → 18) 세 곳이 «문항 수»로 썼다.

| 자리 | 종전 | 고친 뒤 |
|---|---|---|
| `wrongPageHTML()` 의 `need` | `Math.round(s.gapTop)` → 18«문항» | `s.gapQ` → 8문항 |
| 서술문 「더 맞혀야 할 N문항」 | `Math.round(s.gapTop)` — 점수를 문항이라 찍었다 | `s.gapQ` |
| `r.gain >= s.gapTop` | 문항 ≥ 점 — 단위가 다른 비교 | `r.gain >= s.gapQ` |

`s.gapQ` 는 표에 이미 깔린 순서(반 정답률 높은 순 = 회복이 싼 순)대로 **배점을 누적**해
격차를 메우는 데 필요한 문항 수다.

📌 **전 문항 1점이면 증상이 «안» 난다.** 점=문항이라 우연히 맞아떨어지기 때문이다. 그래서
오래 안 보이다가 배점표가 있는 학교에서만 터졌다. 같은 이유로 `pointOf()` 가 1을 돌려주는
시험에서는 `gapQ === gapTop` 이라 **종전과 동작이 같다**(1~15점 전 구간 일치 확인).
`omr.html`(기본판)은 이 기능 자체가 없어 무관하다.

🔴 **원본(`exam-qa/app/OMR진단기_v2.html`)은 아직 안 고쳤다.** 배포본에만 덧댄 상태다
(`배포.sh` 4단계). 원본을 고치면 `gap_fix.pl` 이 「이미 적용됨」만 찍으니 **그때 4단계를 지워라.**

## 🔴 얇은 축이 「약점」을 가져가던 문제 · 학과명 오타 (2026-09-02)

`dist_fix.pl` 이 배포본에 덧대는 두 가지다. **원본으로 승격하면 각각 저절로 건너뛴다** — 그때 `배포.sh` 5단계를 지워라.

### A. 학과명 오타 — 「바이오메이컬공학전공」 → 「바이오메디컬공학전공」

한국외대 자연계열 합격선 줄에 3곳 있었다. 진짜 출처는 `exam-qa` 의

### B. 문항 4개짜리 축이 「약점 1순위」를 가져갔다

2022 한국외대 오전은 `mech` C1·C2(논리·추론) 문항이 **4개뿐**(전체의 8%)인데,
**14명 중 6명의 1순위 약점**을 이 축이 차지했다. 4문항이면 **1문항이 25%p** 라 값이 극단으로 튄다.
🔴 **3/4(75%)를 맞힌 학생까지 「약점」으로 잡혔다.**

```
          s.weak = s.profile.filter(x => x.r <= ov-0.08 || x.r < 0.40)   ← 문항 수 조건이 없었다
```

학생 «자신의» 전체 정답률(`ov`)로 끌어당긴 보정값으로 **판정·정렬만** 한다.
화면에 찍히는 정답률(`x.acc`)은 **실측 그대로** 다 — 숫자를 지어내지 않는다.

```
  radj = (맞힌 수 + 6 × ov) / (문항 수 + 6)        SHRINK=6 ≈ 사전 표본 6문항
```

문항이 많은 축은 거의 안 움직이고 얇은 축만 눌린다. 실측(14명 코호트):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1순위 약점이 5문항 이하 축 | 6/14명 | **2/14명** |
| 강점에 5문항 이하 축이 든 학생 | 3/14명 | **1/14명** |
| 점수·석차·문항 정답률·레이더 | | **완전 불변** |

📌 `computePlan()` 이 `s.weak` 을 물려받으므로 **학습계획·기출추천도 함께 보정**된다.
0/4 처럼 실제로 나쁜 축은 여전히 잡힌다 — 눌러 없애는 것이 아니라 «표본이 얇은 만큼» 끌어당길 뿐이다.

### 아직 안 고친 것 — 「고급 어휘」축은 정보가 없다

🔴 레이더의 「고급 어휘」축 정답률이 **전체 정답률과 늘 같은** 시험지가 있다. 임계값 때문이다.

```js
const awls = qlist.map(q=>km[q].awl).filter(...).sort();
AWLTH = awls[Math.floor(awls.length/2)];      // 시험지별 «중앙값»
// 술어: awl >= AWLTH  →  중앙값이 0 이면 awl=0(학술어휘 전무) 문항까지 전부 포함
```

전 문항의 37%가 `awl=0` 이라 중앙값이 0 이 되는 시험지가 있다. **119개 중 30개(25%)** 가 그렇고
**2022 한국외대 T2·오전 둘 다 포함**된다(세종대·숭실대·중앙대·한양대·홍익대 등).

📌 이 축은 `RADAR`(그래프 8축) 전용이고 `SKILLS`(약점·계획 6축)에는 없다 —
**점수·약점·추천에는 영향이 없고** 레이더 그래프와 영역별 성취도 표만 왜곡된다.

🔴 **고정 임계(코드에 이미 `AWLTH=0.2` 리터럴이 있다)로 바꿀지, 0 을 제외한 중앙값으로 할지는 교육적 판단이라 손대지 않았다.**
고정값으로 바꾸면 축의 뜻이 시험지 간에 «같아지는» 이점이 있다. 다만 `leaders_xy`(학술어휘 축 교차연도 순위)는
빌더가 미리 계산해 넣으므로, 앱만 바꾸면 **앱과 빌더의 축 정의가 어긋날 수 있다** — 함께 고쳐야 한다.

1. **`core.autocrlf=true` 가 HTML 을 줄인다.**
   `.gitattributes` 의 `*.html -text` 로 막아 두었고, 이 저장소는 **첫 커밋 전에** 넣었다.
   🔴 나중에 넣으면 늦는다 — 속성은 **이미 스테이징된 내용을 소급해 고치지 않는다.**
   그때는 `git rm --cached` → `git add` 로 다시 담아야 한다(`exam-dist-2022` 의 `87e5212` 가 그 사고다).
   📌 **「작업 복사본의 해시」와 「저장소 blob 의 해시」는 다른 것이다.**
   검증은 원격에서 **내려받아** 하라: `curl -sL <URL> -o x && sha256sum x`.
2. 🔴 **사내망에서 `git push`·`curl` 이 막힌다.**
   `Recv failure: Connection was reset` · `curl github.com` 타임아웃(HTTP 000).
   **그런데 브라우저는 열린다** — 전체 장애가 아니라 망 정책이다.
   ✅ **네트워크를 바꾸면(핫스팟 등) 통과한다.**
3. **CDN 캐시 10분** — push 직후엔 옛 화면이 보인다. 확인은 `?cb=난수` 로 우회하라.
4. **한글 파일명을 쓰지 않았다.** 저장소 이름·파일명은 URL 경로에 그대로 들어가
   퍼센트 인코딩되면 링크가 길어져 카톡·문자에서 깨진다. 화면 제목은 한글 그대로다.

5. 🔴 **빌더 산출물의 줄바꿈이 바뀐다.** `omr-v2.html` 은 2026-08-31 까지 LF 였는데 09-02 부터 **CRLF** 다.
   `.gitattributes` 의 `*.html -text` 가 양방향으로 바이트를 지켜 주므로 저장소는 멀쩡하다.
   🔴 **문제는 패치 스크립트다** — 여러 줄 패턴을 `"\n"` 으로 굳혀 두면 CRLF 파일에서 «대상 0곳» 이 되어
   배포가 막히고, 넣는 쪽을 `"\n"` 으로 굳히면 혼합 줄바꿈이 생긴다.
   `gap_fix.pl`·`dist_fix.pl` 은 매칭을 `\r?\n` 으로 하고 삽입은 «그 파일이 쓰는» 줄바꿈을 따른다.
   새 패치를 쓸 때도 그렇게 하라.
6. **패치 스크립트는 «전부 검사한 뒤» 고쳐라.** 중간에 `die` 하면 앞 패치만 반영된 파일이 남는다.
   `gap_fix.pl`·`dist_fix.pl` 은 대상 개수를 먼저 다 확인하고 나서 쓴다(파일은 마지막에 한 번만 쓴다).
